Prometheus Adaptive Compute

Dynamic Inference Scheduling for Enterprise AI

Instead of sending every request through the same reasoning pipeline, Adaptive Compute intelligently allocates inference budget based on confidence, improving quality while reducing unnecessary compute.

An adaptive inference scheduler developed for Prometheus at Entain

Kattienger Abhijeet & Shyaam Prasadh  |  Prometheus Squad

Introduction

Over the past year at Entain, we have been building Prometheus, our enterprise AI platform that exposes multiple foundation models through a unified API.

As more engineering teams adopted AI, one trend became immediately obvious:

LLM usage grows exponentially once AI becomes easy to consume.

Every new coding assistant, chatbot, automation workflow, and enterprise application increases inference demand.

The challenge wasn't getting people to use AI. The challenge was scaling AI without scaling infrastructure cost at the same rate.

Why Now

The emergence of reasoning models fundamentally changes inference economics.

Unlike traditional LLMs, reasoning models consume significantly more inference budget on difficult problems. A single reasoning request can cost 10-50x more tokens than a fast model response.

This makes intelligent compute allocation an increasingly important systems problem. The question is no longer just "which model" but "how much thinking."

The Problem

Enterprise AI systems face a fundamental resource allocation problem. Every user query is different, yet most systems allocate identical compute to every request.

Imagine an enterprise AI platform serving:

  • Coding assistants
  • Customer support automation
  • Document search and summarization
  • Data analysts and business intelligence
  • Compliance and regulatory teams

Treating every request as equally difficult means either overspending on simple queries or underperforming on complex ones.

Always Fast

  • Low latency, low cost, high throughput
  • Complex reasoning questions frequently fail

Always Reasoning

  • Better quality on hard problems
  • Higher latency, higher cost
  • Significant compute wasted on simple queries

Neither scales. The question we asked ourselves:

Instead of deciding which model should answer a request,
can we dynamically decide how much compute the request deserves?

That question led to Prometheus Adaptive Compute.

Architecture

Adaptive Compute introduces an intelligent routing layer between users and foundation models. Rather than selecting a model, it estimates confidence, then allocates compute budget accordingly.

Multi-Signal Confidence Estimation

The routing decision combines three types of evidence, without requiring additional API calls:

Query Signals

1

Difficulty

Easy, medium, or hard. Harder questions receive lower baseline confidence.

2

Category

Factual, analytical, multi-step, or opinion. Each contributes differently.

Model Signals

3

Confidence

Self-reported confidence, weighted down (x0.4) because LLMs are overconfident.

4

Source Certainty

How certain the model is about its knowledge source. Uncertain sources lower the score.

Output Signals

5

Answer Quality

Heuristics detect suspicious outputs: short answers to hard questions, explicit refusals.

High confidence: return immediately. Low confidence: allocate additional reasoning budget.

Why fewer signals performed better

We initially hypothesized that adding more routing heuristics would improve confidence estimation.

Experimental results showed the opposite.

Additional heuristic signals increased escalation frequency without improving answer quality. The simpler five-signal estimator produced better routing precision, lower inference cost, and higher overall accuracy.

This is the novel insight: better calibration is more valuable than additional heuristics.

Research Foundation: "Thinking to Recall"

Adaptive Compute is directly inspired by the research paper "Thinking to Recall: How Reasoning Unlocks Parametric Knowledge in LLMs" (Gekhman, Aharoni, Ofek, Geva, Reichart & Herzig, 2026). The paper provides the theoretical and empirical foundation for why adaptive inference scheduling works.

Core Discovery

The paper demonstrates a surprising finding: enabling reasoning in LLMs substantially expands the model's parametric knowledge boundary, unlocking correct answers that are otherwise effectively unreachable — even on simple, single-hop factual questions that don't require multi-step logical decomposition.

This is the key insight that motivated Prometheus Adaptive Compute. If reasoning helps the model recall knowledge it already has but cannot access through standard inference, then the question becomes: when is that extra reasoning budget worthwhile?

Reasoning doesn't just help with complex logic.
It helps LLMs remember what they already know.

Experimental Setup

The researchers used hybrid models (Gemini-2.5-Flash, Gemini-2.5-Pro, Qwen3-32B) where reasoning can be toggled ON/OFF, evaluated on:

  • SimpleQA-Verified — 1,000 factual questions filtered for reliability
  • EntityQuestions — 1,000 template-based single-hop questions across 4 relations

Using the pass@k metric (probability that at least one of k samples is correct), they measured the capability boundary rather than just top-1 accuracy.

Key Finding: Reasoning Expands the Knowledge Boundary

Across all models and datasets, enabling reasoning consistently increased pass@k values. The benefit was often more pronounced at higher k values — in some cases pass@k nearly doubled with reasoning enabled (e.g., Qwen3-32B on SimpleQA-Verified).

This persistent and widening gap suggests that reasoning doesn't just make correct answers more likely — it makes previously unreachable answers accessible.

Reasoning Effectiveness: Less Capable Models Benefit More

The paper defines a unified reasoning effectiveness metric Ω that weights improvements at higher k values more heavily, capturing the boundary expansion effect:

Ω(N) = Σk=1N [ k · (pass@kON − pass@kOFF) / pass@kOFF ] · 1/Σk'

Less capable models showed higher Ω, suggesting they possess more "hidden knowledge" that reasoning helps surface. This directly informs Adaptive Compute's routing strategy: allocate reasoning budget where the model is least confident, because that's where reasoning provides the greatest marginal benefit.

Surprising Finding: Complexity ≠ Reasoning Benefit

Perhaps contrary to intuition, the paper found no evidence that complex or multi-step questions benefit more from reasoning than simple ones. The 95% confidence intervals for "Simple" and "Complex" question subsets overlapped across all models.

This reinforces that reasoning gains are primarily driven by better parametric recall, not multi-hop question decomposition. For Adaptive Compute, this means our confidence estimator should focus on recall difficulty, not question complexity.

Two Mechanisms Behind Reasoning's Effectiveness

1. Computational Buffer Effect

  • Models use reasoning tokens as a latent computation buffer, performing additional internal operations independent of the trace's semantic content
  • Even dummy traces ("Let me think." repeated) substantially improve pass@k over reasoning OFF
  • Effect plateaus and becomes counterproductive beyond ~2048 tokens
  • Proves models can exploit extra forward passes to refine predictions

2. Factual Priming

  • Models engage in generative self-retrieval, constructing contextual bridges by recalling related facts
  • Extracting facts from reasoning traces and providing them as context (without reasoning) recovers most gains
  • Analogous to spreading activation in human semantic memory (Collins & Loftus, 1975)
  • The facts themselves serve as the mechanism, not the reasoning structure

The Computational Buffer: Dummy Traces Still Help

In a remarkable controlled experiment, researchers replaced reasoning traces with semantically meaningless "Let me think." tokens repeated to match the original trace length. The results were striking:

ConditionSimpleQA AccuracyEntityQuestions Accuracy
Reasoning OFF20.6%45.7%
ON Single Dummy (short)22.8%48.2%
ON Dummy (length-matched)26.2%55.4%
Reasoning ON (full)31.4%62.1%

This proves the computational buffer is real — but it cannot fully explain reasoning's benefits. The gap between ON Dummy and full reasoning ON demonstrates that semantic content matters too.

Factual Priming: Facts as Semantic Bridges

When researchers extracted facts from reasoning traces and provided them as context (with reasoning disabled), the model recovered most of the pass@k gains of full reasoning:

This is a powerful validation: the model doesn't need to "reason" about simple factual questions. It needs to recall related facts that serve as associative bridges to the answer. This directly maps to Adaptive Compute's design — when confidence is low, we allocate compute for the model to engage in this self-retrieval process.

The Risk: Hallucinated Facts Propagate

The factual priming mechanism introduces a critical risk. When intermediate facts in the reasoning trace are hallucinated, the probability of a hallucinated final answer increases significantly:

Clean traces (all facts correct)41.4%71.1%
Hallucinated traces (≥1 incorrect fact)26.4%32.2%
Implication for Adaptive Compute: When we route to deep reasoning, we must be aware that the model's self-retrieval process can introduce hallucinated facts that contaminate the final answer. This motivates future work on hallucination detection within reasoning traces.

Compute Budget Scaling: Non-Monotonic Returns

A critical finding for Adaptive Compute's design: more reasoning compute is not always better. The paper showed that increasing dummy trace length initially improves performance but saturates and even becomes counterproductive beyond ~2048 tokens:

This non-monotonic pattern directly informs our routing threshold design. There exists an optimal inference budget for each query — too little and the model can't recall the answer; too much and the extra computation becomes noise.

Connection to Adaptive Compute Architecture

Paper Insight
"Reasoning expands the parametric knowledge boundary"
→
Adaptive Compute
"Allocate reasoning only when the boundary needs expanding"

The paper's findings map directly to our implementation:

  • High confidence (C(q) ≥ τ) → The model's fast inference can access the answer without reasoning. No extra compute needed.
  • Low confidence (C(q) < τ) → The answer lies beyond the fast inference boundary. Allocate reasoning budget for computational buffering + factual priming to expand recall.
  • Calibration matters → The paper shows fewer, well-calibrated signals outperform many noisy signals — exactly what our 5-signal estimator demonstrates.
  • Non-monotonic returns → Our binary routing (fast vs. reasoning) is a practical approximation of the optimal compute allocation curve.

Limitations

The current routing policy has only been evaluated on factual question answering using SimpleQA. While this provides reliable ground truth, more complex workloads, including coding agents, enterprise retrieval, and autonomous agents, remain future work.

Additionally, the confidence estimator relies on signals most informative for factual recall. Different workloads may require different signal combinations and calibration strategies.

Appendix A. Mathematical Formulation

A.1 Problem Definition

Let a user query be q ∈ Q where Q denotes the space of all incoming requests.

The objective of Adaptive Compute is to determine the minimum inference budget required to answer q while maintaining answer quality:

π(q) → b

where π is the routing policy and b is the allocated inference budget.

A.2 Query Classification

Each query is first classified into:

c(q) = (d, t)

where:

  • d = estimated difficulty ∈ {easy, medium, hard}
  • t = query type ∈ {factual, analytical, multi-step, opinion}

A.3 Fast Inference

The fast model Mf produces:

rf = Mf(q) = (a, s, u, m)

consisting of:

  • a = answer
  • s ∈ [0, 1] = self-reported confidence
  • u = source certainty
  • m = metadata

A.4 Confidence Estimation

The confidence estimator combines multiple signals:

x = (x1, x2, ..., x5)

where:

  • x1 = s (model confidence)
  • x2 = fd(d) (query difficulty)
  • x3 = ft(t) (query category)
  • x4 = fs(u) (source certainty)
  • x5 = fa(a) (answer-quality heuristic)

The overall confidence score is:

C(q) = Σi=15 wi xi

subject to 0 ≤ C(q) ≤ 1 and Σ wi = 1.

A.5 Routing Policy

Adaptive Compute performs binary routing:

π(q) = Mf    if C(q) ≥ τ

π(q) = Mr    if C(q) < τ

where Mf = fast model, Mr = reasoning model, τ = routing threshold.

A.6 Adaptive Compute Budget

Instead of viewing reasoning as another model, we define it as additional inference budget. Let Bf be the baseline budget:

B(q) = Bf              if C(q) ≥ τ

B(q) = Bf + ΔB    if C(q) < τ

where ΔB represents additional reasoning compute.

A.7 Optimization Objective

Adaptive Compute seeks to maximize answer quality while minimizing inference cost:

maxπ [ λ A(π) + (1 - λ) K(π) ]

where A = answer accuracy, K = inference cost, and λ balances quality and compute efficiency.

A.8 Routing Outcomes

Each routed request belongs to one of four mutually exclusive states:

Ω = { SF, SR, FM, EU }

  • SF = Fast Path Success
  • SR = Adaptive Compute Success
  • FM = Missed Escalation
  • EU = Unnecessary Escalation

These states define the routing confusion matrix used for evaluation.

A.9 Evaluation Metrics

Router PrecisionP = N(SR) / [N(SR) + N(EU)]
Router RecallR = N(SR) / [N(SR) + N(FM)]
Routing EfficiencyE = [N(SF) + N(SR)] / N

where N is the total number of evaluated queries.

A.10 Inference Budget Reduction

Let Tf be total tokens for fast-only, Ta for Adaptive Compute, and Tr for always-reasoning:

Saving = 1 - (Ta / Tr)

For the SimpleQA evaluation:

Tf26,269
Ta51,367
Tr77,490

yielding a 34% reduction in inference budget compared with always using the reasoning model.
